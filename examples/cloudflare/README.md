# Cloudflare host recipe: the standard agent on PiHarness in a Durable Object

One Worker, one SQLite-backed Durable Object class (`Assistant`) and static assets. Fictional content only.

This is the **same standard agent** the studio runs (`examples/shared/standard-agent.mjs`), with the capabilities Workers can give it, and the **same scenario files** (`examples/studio/scenarios/*.mjs`): the page lists them in the empty chat and `journey.mjs` executes them through the real UI against the deployed URL. The object has a workspace of files in its own SQLite, with just-bash and git over the same files (the page shows them under Files); it has no canvas editor bundle, subagent tasks or code sandbox here, so those parts are simply not passed to `defineStandardAgent`: the agent is told only about what it has, and the scenarios that need more (`['canvas']`, `['subagents']`, ...) are listed disabled with the reason, in the UI and in the journey.

| Need | Where it runs |
|---|---|
| Agent loop, transcripts, recovery | Native Pi Durable, hosted by `PiHarness` (`agents/harness/pi`) in the object; Pi's tables (`pi_*`) are in the object's SQLite |
| Agent definition | `defineStandardAgent` (`examples/shared/standard-agent.mjs`, which wraps `defineAgent` from `@boring/agent/agents`), installed through the registry (`agent.install(registry)`): Pi's `read`, `write` and `edit` behind the file guard, `list_files`, `bash`, `working_git`, `present`, the shared `notes.md`, `share_link`, the schedules, `ask_user` and the skills (`letter-style`, `plain-language`, `letter-review`); self-evolution with approval (see [Self-evolution](#self-evolution-approved-by-the-person)); capabilities reported by `/api/agent` as `variant.capabilities` |
| Workspace (files, presented files, the Shared document panel) | `src/workspace.mjs`: the SQLite workspace backend in the same SQLite, `openSqliteFileSystem` (`@boring/files/sqlite-filesystem`) over `durableObjectSqliteConnection`, one `createWorkspaceProvider` with its journal in the same database (a multi-file save and its receipt commit in one `transactionSync`), and `openVirtualRepository({ fs })` (`@boring/execution/virtual-sqlite`) for Pi's native environment, just-bash and git over the same rows. Data an object held in the earlier layout is moved in once (see [Storage migration](#storage-migration-from-the-earlier-layout)) |
| Chat API | `createChatTransportHandler` from the object's `fetch`; submissions go through `PiHarness` so the object keeps a wake job |
| Browser | `pi-chat`, `ArtifactWorkspace` and the viewers from `registry/`, bundled by `scripts/build-browser.mjs` into `public/` (Workers static assets, plus `scenarios.json`: the scenario descriptions, written at build time from the studio's scenario files), over `createRemoteChat` |
| Model | Workers AI binding, `@cf/moonshotai/kimi-k2.7-code` (Cloudflare's own Pi example uses it for agent work); `@cf/zai-org/glm-4.7-flash` is offered in the picker. No external key. |
| Auth | Bearer token in the Worker secret `ACCESS_TOKEN` (the operator, the owner's object only), a signed-in person's session cookie (their own object), or a view link's session (one conversation); checked in the Worker (constant time) before the object is woken. See [Public signup](#public-signup-one-agent-per-person) |

## Deploy

Prerequisites: Node 22.19+, a Cloudflare account on a plan with SQLite-backed Durable Objects (the Workers Free plan supports them), Workers AI enabled, and `CLOUDFLARE_API_TOKEN` with Workers Scripts, Durable Objects and Workers AI permissions.

```sh
npm ci --ignore-scripts
npm run cloudflare:build                      # packages + browser app into examples/cloudflare/public
mkdir -p .cache && openssl rand -hex 24 > .cache/cloudflare-recipe-token   # .cache/ is gitignored
npx wrangler deploy --config examples/cloudflare/wrangler.jsonc            # first deploy creates the Worker
npx wrangler secret put ACCESS_TOKEN --config examples/cloudflare/wrangler.jsonc < .cache/cloudflare-recipe-token
```

Open `https://boring-ui-v4-recipe.<your-subdomain>.workers.dev/#token=<contents of the token file>` (the fragment is removed from the address bar and the token kept in `sessionStorage`), or open the page and paste it. The token is never a query parameter.

Journey in a real browser: `CF_URL=<url> CHROMIUM=<binary> node examples/cloudflare/journey.mjs`. It checks the 401s and the token gate, then runs every shared scenario the deployment's capabilities allow (`CF_ONLY=chat-basics,artifacts` or scenario ids to run some), lists the others as disabled with their reason, and finishes with the atomicity proof. The `chat-restart` scenario resets the Durable Object through `/api/debug/restart` and checks that a new in-memory instance serves the same conversation.

Delete: `npx wrangler delete --config examples/cloudflare/wrangler.jsonc` (removes the Worker and its Durable Object data).

## WhatsApp and a ChatGPT subscription (optional)

The same object can answer on WhatsApp (Meta Cloud API) through the channel gateway in `examples/whatsapp`. `src/whatsapp.mjs` is a Lifecycle capability: `/whatsapp` is checked by Meta's signature (not the bearer token). Each allow-listed sender gets a conversation of their own, which also appears in the page's History. Messages are admitted through `PiHarness`, so a running answer survives eviction. A recurring Lifecycle job sends replies still owed after a restart.

| Worker secret | Value |
|---|---|
| `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID` | the Meta app's system-user token, app secret, a verify token you choose, the business number ID |
| `WHATSAPP_ALLOWED` | comma-separated WhatsApp IDs (digits, no `+`) of the owner, answered by the owner's object (`main`); with public signup, other people's numbers come from the registry; everyone else is acknowledged and ignored |
| `CHATGPT_CREDENTIAL` (optional) | a ChatGPT-subscription sign-in for the model, made once with `node examples/cloudflare/scripts/chatgpt-login.mjs`. It seeds the object's storage, where pi-ai refreshes it. `CHATGPT_MODEL` overrides `gpt-5.5` |
| `OPENAI_API_KEY` (optional) | an OpenAI API key instead; preferred when both are set |

Without a model secret the agent uses Workers AI. Then point the Meta app's webhook at `https://<worker>.workers.dev/whatsapp` (field `messages`, the same verify token) and subscribe the app to the WhatsApp Business Account.

`CLOUDFLARE_API_TOKEN=<token> node examples/cloudflare/whatsapp-journey.mjs` runs `wrangler dev` with fictional WhatsApp secrets and a local stand-in for the Graph API (it never contacts Meta). Its model is Workers AI by default (no model secret). It never reads the deployment's `.cache/chatgpt-credential.json`: a local run would refresh it and rotate the refresh token the deployed Worker was seeded with. To use ChatGPT, sign in separately (`node examples/cloudflare/scripts/chatgpt-login.mjs .cache/journey-chatgpt-credential.json`) and pass `JOURNEY_CHATGPT_CREDENTIAL=.cache/journey-chatgpt-credential.json`; `JOURNEY_MODEL=openai` uses `OPENAI_API_KEY`. Its secrets file and wrangler state (`--env-file`, `--persist-to`) live in a fresh temporary directory that it deletes; the default `.wrangler/state` is never touched, and `wrangler dev` runs in its own process group that is stopped even when a step fails. It checks:
- the subscription challenge;
- signature and verify-token refusals;
- an unknown sender left unanswered;
- the read mark and typing indicator;
- the agent's answer;
- no second answer to a redelivered webhook;
- the conversation in History;
- a reply still delivered after the object is reset, at two boundaries held deterministically by debug-only holds (`/api/debug/holds`): before the answer is generated (the model stream of that message waits; the submission is `placed`) and after it settled but before the Graph send (the gateway's `beforeSend` waits; the submission is `done`). In both cases `/api/debug/restart` resets the object while it waits, no request reaches the Worker afterwards (only the Graph stand-in is polled, so the wake alarm alone restarts it), exactly one reply arrives, and the native submission read through `/api/chat?op=submission` has the same id before and after and ends `done`;
- the default `.wrangler/state` unchanged, the temporary state deleted and `wrangler dev` stopped.

## Links the agent sends: the editable workspace

The agent's `share_link` tool (a workspace file path, presented files included, or `notes: true`) returns `/v/<payload>.<signature>`: HMAC-signed with a key derived from `ACCESS_TOKEN`, valid 7 days, naming the item and the conversation it was made in (on WhatsApp, the sender's conversation). Opening it serves the app page; the page exchanges the link for a session (`POST /api/session`, the link is the credential) and opens the web workspace on that conversation: the chat beside the item in its editor (file: the studio file viewer over `/api/resources`, revisioned, a change the agent made behind the editor is a conflict, never overwritten; notes: the shared document `notes.md`; a link made before artifacts became files names an artifact id, and opens the file it was moved to). On a phone the item comes first, full screen, with a Chat button; the chat's Document and Files buttons go back. `/v/<link>?raw=1` is the read-only preview: the page at the link's URL is fixed and runs no script; the item is escaped into one sandboxed `srcdoc` frame (scripts for HTML only, never same-origin, top navigation, popups or forms; no referrer, `frame-src 'none'`), so generated content can neither read the link nor navigate away with it. The web workspace's HTML preview runs pages the same way (sandboxed `srcdoc`, opaque origin), after the page has already taken the link out of its address.

- A session token is signed with a different derived key (a link is never a bearer, a session never a link), has scope `link` (the object that made the link, and in it only the link's conversation: read it and chat in it, plus the item editors; no other conversation, no new ones, no debug routes) and lasts 24 hours (`SESSION_TTL_SECONDS` shortens it). The Worker verifies it by HMAC; nothing logs tokens, but the platform's request logs show `/v/...` paths. The open page renews its session from the link (kept in `sessionStorage`) until the link expires, and exchanges the kept link again before loading after a reload. The Worker forwards a session's verified expiry to the object (any client copy of that header is removed), so an open chat watch ends when the session expires. **Anyone who has a link can read and chat in that one conversation, and edit the workspace items, of that one agent for up to 7 days:** send links only to their person.
- The editors save through the one workspace provider (`/api/resources`, see Workspace below): a save is conditional on the revision the editor read, so a change the agent made behind the editor is a conflict, never overwritten. A command (bash, git, an agent-written tool) runs in the provider's mutation queue, so a save never lands while one runs. `node --test test/packages/cloudflare-workspace.test.mjs` covers this, interrupted saves and the move of the earlier layout, with an in-memory Durable Object storage.
- `CLOUDFLARE_API_TOKEN=... CHROMIUM=<binary> node examples/cloudflare/links-journey.mjs` runs `wrangler dev` (Workers AI, fictional WhatsApp, a 60 s session) and a real Chromium: the link opens with no stored token on the WhatsApp conversation, the file is edited and saved (read back through `/api/file`), the agent sees the change, a change by the agent gives a conflict, tampered, forged and expired links are refused, expired sessions are refused while the page renews, and a phone shows document, then chat. Its model, secrets file and state follow the WhatsApp journey's rules (Workers AI by default, ChatGPT only with a separate `JOURNEY_CHATGPT_CREDENTIAL`, `--env-file`/`--persist-to` in a deleted temporary directory, default state and `.dev.vars` untouched). Evidence: `.cache/evidence/cloudflare-links/`.

## MCP servers (optional)

`src/mcp.mjs` connects the agent to remote MCP servers. Cloudflare's `MCPClientManager` (`agents/mcp/client`) is installed on the object's Lifecycle, before PiHarness: it keeps each server in the object's SQLite (`cf_agents_mcp_servers`), reconnects after a restart or eviction, and runs MCP OAuth. Each server becomes one native extension `mcp.<id>` built by `@boring/agent/mcp` (tools named `<id>__<tool>`), installed in the agent's registry and kept out of the Harness default selection (`withoutMcpByDefault`). Tool lists are cached in the object, so a call replayed after a restart finds its tool before the server has reconnected.

Configure with the Worker variable (or secret) `MCP_SERVERS`, a JSON array:

```json
[{ "id": "gmail", "url": "https://backend.composio.dev/v3/mcp/<server_id>?user_id={user}", "headers": { "x-api-key": "COMPOSIO_API_KEY" },
   "allow": ["GMAIL_FETCH_EMAILS", "GMAIL_SEND_EMAIL"], "approve": "writes" }]
```

- `headers` maps a header name to the **name** of a Worker secret (`npx wrangler secret put COMPOSIO_API_KEY`); the value goes to that server only, is removed from tool results and errors, and never reaches the model or the transcript. The manager persists it with the server row in the object's SQLite.
- `{user}` in the URL is replaced by `MCP_USER_ID` (default `owner`): one owner per object for now.
- `allow` lists the upstream tool names to expose (`"all"` exposes every listed tool). `approve`: `"writes"` (default) asks the person before any tool the server does not mark `readOnlyHint`; `"none"` never asks. On WhatsApp the question arrives with Approve and Deny buttons and the reply answers it; on the web it is the approval card.
- `oauth: true` for a server that signs the person in with MCP OAuth: the agent's `connect_service({ id })` returns the sign-in link (it can send it on WhatsApp), and the provider redirects to `/api/mcp/callback`, which the Worker forwards without the bearer token (the manager checks the state it issued). The public origin is the one the object last saw a request on.
- Grants: WhatsApp conversations of allowed senders, and web conversations created with `POST /api/conversations {"services": true}`, select the servers; every other conversation never sees them, and each call checks the grant again. `GET /api/services[?conversation=<id>][&wait=1]` shows each server's state and tools, and for one conversation whether it is granted and what it selects.
- Composio connects a person's Gmail through its own connected-accounts API (no MCP OAuth). A `connect_account({ toolkit })` host tool belongs in `McpServices`' `hostTools` (the services extension); it is not built yet.
- `CLOUDFLARE_API_TOKEN=... node examples/cloudflare/mcp-journey.mjs` runs `wrangler dev` (Workers AI, fictional WhatsApp) against a fictional notes MCP server (`mcp-fixture.mjs`, Streamable HTTP on 127.0.0.1 behind an `x-api-key` check): the read tool answers, a write is asked on WhatsApp and runs once on Approve and never on Deny, the key reaches the server but not the transcript or replies, the server reconnects after an object reset, and an ungranted conversation never reaches it. Evidence: `.cache/evidence/cloudflare-mcp.json`.

## Scheduled tasks

Say on WhatsApp (or in the web chat) "every weekday at 8, summarise my unread mail" or "remind me Friday 17:00 to call the fictional plumber". The agent calls `schedule_task` (name, instruction, `when`, optional `timezone`); you approve it like any write, with Approve and Deny buttons on WhatsApp. When it is due, the instruction arrives in the same conversation as `[Scheduled task "<name>" (<id>)] <instruction>`, the agent runs a normal turn, and on WhatsApp its answer is sent to you. `list_schedules` and `cancel_schedule` need no approval. A scheduled run has no more permission than any turn: a Gmail write in it still asks you.

- `when` is a 5-field cron in local time (`0 8 * * 1-5`), a local ISO date-time (`2026-10-09T17:00`; with `Z` or an offset it is absolute) or a delay (`30m`, `2h`, `1d`). Times are local to `SCHEDULE_TIMEZONE` (default `Europe/Zurich`) unless the person names another IANA zone. Cloudflare's Scheduler runs crons in UTC, so a local cron is stored as a UTC cron covering every offset the zone uses (`0 8 * * 1-5` in Zurich becomes `0 6,7 * * 1-5`) and only the firings that are 08:00 in Zurich run: summer and winter time both work, and the two UTC firings of one local minute when the clocks go back run once. A local date-time that a DST change skips is refused; zones with non-whole-hour offsets take a UTC cron only.
- Limits: at most 20 schedules per object, recurring ones at most every 15 minutes, instructions up to 2000 characters, one-shots between one minute and one year ahead.
- Storage and wake-up are Cloudflare's `Scheduler` (`agents/schedules`, experimental) on the object's existing Lifecycle: no alarm or table of ours. Each occurrence is submitted with the request ID `schedule:<id>:<local minute>` (one-shots: their instant), so a retried or repeated callback submits once; the answer is owed like a WhatsApp reply, so it survives a restart.
- WhatsApp's 24-hour rule: free-form messages reach a person only within 24 hours of their last message. A scheduled answer due later is held and sent as soon as you next write (an approval question in the run waits the same way and cannot be answered before you see it). With `WHATSAPP_WAKE_TEMPLATE` set to an approved template with no variables (language `WHATSAPP_WAKE_TEMPLATE_LANG`, default `en_US`), for example "A scheduled task has a result: reply to see it.", that template is sent once per held period to invite you to write. A template does not reopen the window for free-form text, so the answer itself still waits for your reply. Held answers are logged (`whatsapp answer held for the 24-hour window`).
- `GET /api/schedules` (owner bearer or a session) lists them: each record (`id`, `name`, `prompt`, `when`, `timezone`, `conversation`, `createdAt`, `approvedBy`) with a description and its next run.
- Code: `src/schedules.mjs` is portable (record, validation, request ID rule, `fireSchedule`, the tools over a host backend `{ set, list, cancel }`); `src/schedules-cloudflare.mjs` binds that backend to the Scheduler. Proof: the scheduled-task case in `test/packages/whatsapp-channels.test.mjs` (approval on the channel, a doubled firing submitted once and answered, an answer outside the window held with one invite and released by the next message).

## Public signup: one agent per person

Anyone can sign up and get an agent of their own. Off unless configured (without `HUB_ISSUER` the Worker is single-owner as before).

1. `GET /` (signed out) is a one-screen landing page served by the Worker (`src/signup.mjs`, plain HTML/CSS, light and dark, no secure-context API so plain-HTTP localhost works): the WhatsApp number and **Get my agent**. `/#token=...` and `/#operator` still open the web app for the operator.
2. `POST /signup` keeps the claimed number with the OIDC `state`, `nonce` and PKCE verifier in a signed 10-minute cookie and sends the browser to the hub (`src/oidc.mjs`): authorization code + PKCE S256, scope `openid email profile offline_access hub:whatsapp`, endpoints from `HUB_ISSUER/.well-known/openid-configuration`, `resource` = `HUB_RESOURCE`. The hub (its signup contract rev 2: hachej/boring-hub#76; the Worker uses only discovery, authorize, token and `POST /v1/app/whatsapp-identity`, not the per-message `GET` or `DELETE`) offers Google or an email code and brands the page from the resource.
3. `GET /auth/callback` exchanges the code (confidential client, `client_secret_basic`), verifies the id_token with Web Crypto against the JWKS (`iss`, `aud`/`azp`, `exp`, `iat`, `nonce`; EdDSA, ES256 or RS256), keeps the person's hub grant (access token, refresh token) in the person's own object only (never in the registry, the browser or a log), sets the person's session cookie (HttpOnly, SameSite=Lax, 30 days) and issues a one-time code (6 characters without look-alikes, 10 minutes, single use, bound to the hub subject, email and claimed number) in the registry object (`src/registry.mjs`, class `Registry`, one instance). On a phone the page opens `https://wa.me/<WHATSAPP_PUBLIC_NUMBER>?text=START%20<code>`; on a computer it shows the code and the link.
4. The webhook (`POST /whatsapp`): the Worker verifies Meta's signature (the object verifies again, unchanged). `START <code>` from number N is accepted only if the code is unexpired, unused and was claimed for N (E.164); the registry then routes N to the person, the person's object is told (`adopt`), the hub gets `POST /v1/app/whatsapp-identity { subjectToken, phone }` (`HUB_APP_KEY` as bearer, the person's access token as proof: the hub takes the person from that token, never from the app key; a Lifecycle job in the person's object refreshes the 15-minute access token first when it expired, so a late START still links, and retries throttling (429, after `Retry-After`), 5xx and network failures of both the refresh and the link (only a 400/401 refusal of the grant is final); the obligation is written in the same storage write as the phone adoption and re-armed on replay and restart; obligation and grant carry versions, and a job settles or deletes only the versions it processed; then the grant is deleted), and N gets "You're set up". A wrong, used or expired code gets a refusal pointing to the landing page; a number that already belongs to another person (or is one of the owner's `WHATSAPP_ALLOWED` numbers) is never moved: START is refused with "contact the operator" (as the hub answers 409 `phone_already_linked`). Two concurrent STARTs with one code link once (the registry serializes redemptions). The redemption, the routing, the membership and an obligation to tell the person's object are one registry write; the Worker then calls `adopt` and confirms, and the registry's alarm retries any adoption not confirmed (a Worker that died in between). A redelivered START whose redemption was committed always completes, also once the code is gone or sign-ups are closed. An unknown number without START gets "sign up at <origin>" at most once a day. Every other message goes to its sender's own object only: a mixed-sender webhook is split per object and each part re-signed with the app secret, so the object's unchanged signature check passes. Each object also asks the registry before admitting a message and before sending a scheduled reply, so the registry alone decides who talks to which agent.
5. One agent per person: `env.ASSISTANT.getByName('p-' + 32 hex of SHA-256(issuer, subject))`. Each has its own conversations, files, schedules and memory; Workers AI only (`MODELS`, never the owner's ChatGPT), at most `SIGNUP_DAILY_TURNS` turns a day (default 50): one reservation per input, atomic and keyed by conversation and request ID at the one admission boundary (web, WhatsApp and scheduled runs alike), counted against the day it was first reserved and kept for the redelivery window (8 days), so a retry or redelivery reuses it, even the next day; a reservation is released only when its input will never be a turn: neither in Pi's submissions nor still owed by the WhatsApp gateway (whose recovery of an owed input goes through the same admission path, new gateway option `conversation`, so it reuses the reservation and never makes an unreserved turn); checked at once after a failed submit and by reconciliation when the cap is reached; on WhatsApp it applies only once the gateway has classified a message as new input (`admitInput`), so an answer to an open question or a redelivery is never capped; past the cap a friendly WhatsApp message, a 429 on the web, and, with `COMPOSIO_API_KEY`, its own Composio Tool Router session created on first need (`src/composio-session.mjs`: `POST /api/v3.1/tool_router/session` with `user_id` = the person id, stored in the person's object; the approval policy is unchanged).
6. The Worker decides who may use the bot: its own registry routes every number. Linking at the hub does not make the person a member of the app in the hub (and the Worker does not call the hub's `GET /v1/app/whatsapp-identity` per message).
7. Schedules belong to their conversation: `list_schedules` and `cancel_schedule` see only the calling conversation's schedules (a link session's conversation cannot reveal or cancel others); `GET /api/schedules` still lists all of them for the owner's or person's own web session.
8. The owner keeps `main` and its conversations: `WHATSAPP_ALLOWED` numbers go there, `ACCESS_TOKEN` is operator access to `main` only (debug routes included), and `OWNER_SUBJECT` (the owner's hub subject) makes the owner's own sign-in land on `main` too.
9. Web sessions: a person's cookie reaches only their object, and only once their START was redeemed (registry membership, checked on every request): before that the session is onboarding only (403 `phone-not-linked`, `/` stays the landing page), so nobody gets the model or services without proving a number; (writes only with this origin's `Origin` header); a view link names its object, and its session reaches only that object's linked conversation. Debug routes stay operator-only.

| Setting | Value |
|---|---|
| `HUB_ISSUER` (var) | the hub's exact issuer: `https://<hub>/api/auth` |
| `OIDC_CLIENT_ID` (var), `OIDC_CLIENT_SECRET` (secret) | the confidential client registered at the hub (`HUB_CLIENT_ID` / `HUB_CLIENT_SECRET` also accepted); redirect URI `<origin>/auth/callback` |
| `HUB_APP_KEY` (secret) | the hub workload key for `/v1/app/*` (scope `whatsapp`) |
| `HUB_RESOURCE`, `OIDC_REDIRECT_URI`, `HUB_URL`, `OIDC_SCOPE` (vars, optional) | defaults derived from the request origin: `<origin>/api`, `<origin>/auth/callback`; then the issuer's origin and `openid email profile offline_access hub:whatsapp`. They must equal what the hub registered (see below) |
| `WHATSAPP_PUBLIC_NUMBER` (var) | the agent's WhatsApp number (`+41...`), for the wa.me link |
| `SIGNUP_OPEN` (var) | `1` accepts signups; anything else: the landing page says closed, new people and new number links (START) are refused; people already linked keep working on WhatsApp and can sign in again on the web (**Already have your agent? Sign in**: no number, no code) |
| `OWNER_SUBJECT` (secret) | the owner's hub subject, mapped to `main` |
| `SIGNUP_DAILY_TURNS`, `SIGNUP_DEFAULT_COUNTRY` (vars, optional) | default `50` and `41` (a national number `079...` becomes `+4179...`) |
| `COMPOSIO_API_KEY` (secret, optional), `COMPOSIO_TOOLKITS` (var, optional) | per-person Composio sessions; toolkit slugs to enable (default: Composio's) |
| `APP_NAME`, `APP_TITLE`, `APP_VERSION`, `APP_DESCRIPTION` (vars, optional) | the manifest at `/.well-known/boring.json` (`{ protocol: 1, name: "boring-whatsapp-agent", version, title, description, agents, jobs, conversations, tools, endpoints }`) |

Deploy under the name you registered with the hub (`npx wrangler deploy --config examples/cloudflare/wrangler.jsonc --name <worker>`; the default name in `wrangler.jsonc` stays the recipe's). The hub registers the resource `https://<worker origin>/api` and the redirect `https://<worker origin>/auth/callback`, which are the defaults on that origin; set `HUB_RESOURCE` and `OIDC_REDIRECT_URI` explicitly if the Worker is reached on another origin. Local dev uses the hub's separate dev client with `OIDC_REDIRECT_URI=http://127.0.0.1:8787/auth/callback` (exactly `127.0.0.1`).

`ACCESS_TOKEN` must be set: it signs the cookies, links and sessions (each with its own derived key). `wrangler.jsonc` binds `REGISTRY` and adds migration `v2` (`new_sqlite_classes: ["Registry"]`); the next deploy applies it.

**Meta test numbers:** until the real business number is live, Meta's test number only sends to recipient numbers pre-registered in the Meta app (up to five). A person whose number is not on that list can sign up and send START (inbound works) but never receives the replies.

## Self-evolution, approved by the person

Every object (the owner's `main` and each person's `p-…`) is self-evolving in its own workspace ([SELF-EVOLUTION.md](../../docs/architecture/SELF-EVOLUTION.md), laws SELF-1..4 in [packages/agent/README.md](../../packages/agent/README.md#self-evolution)): the agent writes standing instructions, skills and tools into `.agent/` with its ordinary file tools, and its tools run in that object's just-bash like `bash`, never in the Worker. The object passes `selfEvolving: { approval }`, so:

- Writing to `.agent/` needs no approval, but nothing written there takes effect until a reload is approved: the instructions shown are those of the last approved reload (approval compares the exact text, so a reordering asks too), and agent-written tools run only while every file under `.agent/` (instructions and skills included) is byte for byte what was approved, checked and run inside one operation of the workspace's mutation queue.
- The agent's `reload` asks the person first, through the existing approval question: on the web the approval card, on WhatsApp the question with Approve and Deny buttons ("Allow reload? Instructions: 3 line(s) added, 1 removed (240 characters now). Skills: added tide-tables. Tools: added word_count."). Approve applies exactly the state that was summarised (if `.agent/` changed while the person decided, nothing is applied and the agent is told to reload again); Deny changes nothing.
- A WhatsApp message that is exactly `/reload` runs the same reload for the person at once (their own command is their approval), without a model turn and without counting against the daily cap, and the report comes back as a reply. The approved state and the record that this message applied it are one write, so a redelivered message gets the same report and approves nothing newer. Only the object's own person can send it: the Worker routes a sender only to the object the registry gives their number (or `main` for the owner's allow-list), and the object checks that again on every message.
- The approved state is kept in the object's SQLite (`boring_self_evolution`) and installed again whenever the object opens (`DefinedAgent.restore()`), so it survives restarts; what was written but not approved never takes effect on its own.

## Storage migration from the earlier layout

Objects created before the files rework keep their data in the earlier layout: the agent's files saved path by path, and a separate store of published documents (the shared notes and artifacts). `src/legacy-storage.mjs` records the storage layout (`boring_storage_version`, 2 here; a newer one is refused) and, when an object opens with earlier-layout data, moves it into the workspace in one SQLite transaction (a crash leaves everything as it was and the next open runs it again), then renames the old tables `boring_legacy_*`; nothing is deleted.

- Files and folders keep their paths, bytes and times (and `.git`, so the history is the saved one). Modes are not kept (every file reads 0644). Symbolic links cannot exist in the new backend: they are not moved, only counted (their rows stay in `boring_workspace_links`). A workspace the earlier layout initialized is never seeded again, even when its `.git` was deleted; an emptied workspace stays empty.
- Each published document's latest version becomes a workspace file at the first free (or identical) place among `<path>`, `documents/<path>`, `documents/<revision>/<path>`, `legacy-documents/<revision>/<path>`, never over another file; the move commits only when every document has one. Where each landed is kept; the shared notes follow it everywhere (the page's Document button, links, the editor and the agent's instructions name the same file). Older document versions stay only in the renamed tables. Artifact view links made before the change open the file the artifact landed in; artifact cards in old transcripts still name the removed `documents` provider (open those files from Files or a link).
- **Upgrading: roll forward only.** Running the pre-migration Worker against a moved object is not supported: it cannot read the new file table. Fix forward with a newer build instead. The old tables stay as `boring_legacy_*` (files, documents, versions; links, directories and meta under their old names) for manual recovery, and a database written by a newer layout is refused rather than misread. (If a previous Worker did run and recreated its document tables, the next open moves those documents in beside the existing files; `test/packages/cloudflare-workspace.test.mjs` covers that the object still opens.)
- `node --test test/packages/cloudflare-workspace.test.mjs` proves the move against a fixture in the earlier layout (`test/fixtures/cloudflare-legacy-storage.mjs`): collisions at every named destination, the notes beside an agent `notes.md`, a deleted `.git`, an interrupted move and documents recreated by a previous Worker. No wrangler migration is needed: the class and its SQLite storage are unchanged.

## Proofs built in

These routes are off by default and answer 404 on a deployment. Turn them on only for a proof run: `npx wrangler dev --config examples/cloudflare/wrangler.jsonc --var ENABLE_DEBUG_ROUTES:1` (or `ENABLE_DEBUG_ROUTES=1` in a gitignored `.dev.vars`), and run the journey with `CF_DEBUG_ROUTES=1`. Without `CF_DEBUG_ROUTES=1` the journey asserts they are 404 and skips the two proofs. Never set the variable on a deployed Worker.

- `POST /api/debug/restart` resets the object (`ctx.abort`); `/api/agent` returns an `instance` id that changes on restart while conversations and documents stay.
- `GET|POST /api/debug/holds` and `POST /api/debug/holds/release` list, arm (`{ "boundary": "generation" | "delivery", "match": ... }`) and release one-shot in-memory holds (`src/debug-holds.mjs`): `generation` makes the model stream whose newest user message contains `match` wait before it starts, `delivery` makes the WhatsApp gateway wait before sending the reply of requestId `match`. Without the variable nothing is wrapped: the model provider is used as is and the gateway gets no `beforeSend`.
- `POST /api/debug/atomicity` runs a two-file save in a separate proof workspace whose second history insert fails after both file rows, the receipt and the first history row were written, and reports that everything rolled back.

## Limits and notes

- Beta: `PiHarness` and `agents/models/pi-ai` may change. `agents@0.26.0` peers `@modelcontextprotocol/sdk@1.30.0`; the repo pins 1.31.0, so `package.json` overrides that peer. Installing `MCPClientManager` directly on a Lifecycle (outside `agent.mcp`) is marked experimental by Cloudflare.
- One object per person: the owner's is `getByName('main')`, a signed-up person's `getByName('p-<32 hex>')` (see Public signup). The watch stream is an open HTTP request: the object stays active while a page is open (duration billing). A dropped stream reconnects.
- The workspace's SQLite connection is synchronous on purpose (see `SqliteConnection` in `@boring/files/sqlite`); Pi's own async `SqliteDatabase` is used by `PiHarness` for Pi's tables.
- The shell is just-bash over the workspace rows, with `git` (isomorphic-git, no remote): regular files and directories only (no links; `chmod` changes nothing) and no processes. A real shell (Cloudflare Sandbox or Containers behind a Pi `ExecutionEnv`) would be a variant supplying an `ExecutionEnv`, not a change to the agent. Canvas, subagents and code mode are omitted: the tldraw editor and the QuickJS sandbox are not bundled in this Worker.
- Replay: tools are `unsafe` by default, so a tool interrupted by a reset reports an interruption instead of running again.
